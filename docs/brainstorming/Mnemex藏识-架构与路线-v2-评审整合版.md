# Mnemex / 藏识 — 架构与路线 v2（评审意见整合版）

> 本文基于外部设计评审报告，对《个人知识与代码管理系统-产品路线规划》和《Mnemex藏识-产品与设计深化建议》做出的修订整合，作为后续实现的当前基线。原文档保留作为历史记录，本文档中的结论优先级更高。

---

## 一、定位收敛

**从**："文档+代码持续采集、总结、分析、检索、共享记忆"的全能知识管理平台
**收敛为**："AI Agent 的本地工程记忆引擎"（Local Engineering Memory Engine for AI Agents）

第一阶段只解决一个问题：**让 AI Agent 能可靠理解一个工程项目**。个人技术画像、跨项目模式挖掘、通用文档管理这些能力不是不做，而是明确排在工程记忆能力打磨扎实之后，避免 MVP 阶段就承担"AI IDE + PKM + Agent 平台"三重复杂度。

---

## 二、架构修订：新增 Knowledge Object 层

**原架构**：文件 → chunk → embedding
**修订为**：文件 → Knowledge Object → chunk → embedding

Agent 需要的不是文件片段，而是可以直接引用和推理的知识实体。新增实体类型：

| 类型 | 说明 |
|---|---|
| `CodeSymbol` | 函数/类/模块级别的代码单元，带调用/继承/import 关系 |
| `DesignDecision` | 从 commit/文档中提炼的"问题-诊断-方案"三元组 |
| `BugRecord` | 调试记录、根因、修复方案 |
| `DocumentSection` | 文档按章节切分后的语义单元 |
| `CommitEvent` | Git 提交作为一等事件，关联受影响的 Knowledge Object |

这一层是此前设计中缺失的一环，chunk/embedding 仍然存在，但作为 Knowledge Object 的底层实现细节，检索和关联图谱都应该以 Knowledge Object 为基本单位，而不是裸 chunk。

---

## 三、图谱策略澄清

**存储技术选型**：Phase 0-3 阶段用 SQLite `knowledge_node` / `knowledge_edge` 两张表 + 递归 CTE 即可，不提前引入 KuzuDB 等嵌入式图库。真正的瓶颈是关系抽取的质量，不是存储引擎的能力上限，过早引入额外数据库依赖只会增加维护成本。

**关系抽取本身不能延后**：需要明确区分两类"关联能力"——

- **结构关联**（调用/import/继承、commit 影响范围）：这是"让 Agent 理解一个工程项目"的核心组成部分，属于 Phase 0-1，不能往后放。没有结构关联，Agent 看到的仍然是孤立文件。
- **行为关联**（跨会话主动提醒、跨项目模式挖掘）：依赖长期使用数据积累，面向个人使用习惯而非工程理解本身，这类留在 Phase 3-4。

---

## 四、检索链路：新增 Ranking Pipeline，明确轻量/深度双路径

**原设计**偏重召回（向量检索 + 关键词），容易出现"找到很多相关内容，但不是最有用的内容"。

**修订为**两条路径，按场景选择，而非每次检索都走完整链路：

```
轻量路径（默认，日常检索/主动提醒）
Query → Keyword Search → Vector Search → 直接返回

深度路径（用户主动请求"深入分析"/复杂跨文件综合）
Query → Keyword Search → Vector Search → Graph Expansion → Reranker → LLM Context Builder
```

理由：Graph Expansion + Reranker 对检索质量提升明显，但在本地小模型场景下会显著增加延迟，日常高频检索走轻量路径保证响应速度，深度路径按需触发。

---

## 五、Memory 生命周期（取代/整合此前"知识健康度"概念）

此前深化建议中提出的"知识健康度扫描"，与评审提出的 Memory 生命周期本质是同一件事，合并为一套字段设计而非两个并行概念：

```
创建 → 验证 → 强化 → 衰减 → 归档
```

每个 Knowledge Object 携带：

| 字段 | 说明 |
|---|---|
| `confidence` | 该知识的可信度，随验证/矛盾检测调整 |
| `usage_count` | 被检索/引用次数 |
| `last_used` | 最近一次被使用的时间 |
| `freshness` | 与当前代码/文档状态的一致性评分 |
| `contradiction_score` | 是否与其他 Knowledge Object 存在冲突 |

`contradiction_score` 高、`freshness` 低的实体自动标记为"可能过时"，这就是"知识健康度"在数据层面的具体实现，不需要额外单独设计一套健康度指标。

---

## 六、MCP 定位修订：降级为 Adapter，不作为核心业务层

**原设计**：核心逻辑与 MCP Server 耦合较紧
**修订为**：

```
核心：Memory Engine（Knowledge Object + 检索 + 图谱 + 生命周期管理）
        ↓
适配层：MCP Server / HTTP API / CLI / IDE Plugin
```

这与此前"记忆层与协议层解耦"的判断方向一致，评审从多客户端兼容角度（Cursor、Continue、自研 Agent 无需修改核心即可接入）给出了同样的结论，两者互相印证，确认这是正确方向。此前提出的"MCP tool 需要显式 scope 句柄"的要求，在 Adapter 层实现即可，不影响核心引擎设计。

---

## 七、本地 AI 策略分级

**原设计**：本地默认（7B 摘要模型）+ 云端可选，二元切换
**修订为**四级策略，按任务复杂度自动选择，而非全局一刀切：

| 级别 | 能力 | 适用场景 |
|---|---|---|
| L0 | 规则摘要（无模型） | 文件元数据、简单结构化摘要 |
| L1 | 小模型 embedding | 语义检索、相似度匹配 |
| L2 | 本地 3B-7B 摘要模型 | 日常文件/模块摘要 |
| L3 | 云端增强 | 复杂跨文件综合分析，用户显式开启 |

多数高频操作（尤其是轻量检索路径）应该尽量停留在 L0/L1，只有真正需要语言生成能力的任务才触发 L2，缓解"7B 模型对普通用户机器压力较大"的风险。

---

## 八、路线图修订

**原 Phase 0-6** 调整为：

| Phase | 内容 | 备注 |
|---|---|---|
| Phase 0 | 文件扫描 + Git 分析 + AST 解析 + SQLite 基础设施 | 不含向量检索 |
| Phase 1 | 工程知识库：Knowledge Object 建模、符号级检索、决策记录抽取、项目摘要、结构关联图谱 | 核心 MVP，"让 Agent 理解项目"在此阶段完成 |
| Phase 2 | Agent Memory 开放：Memory Engine 核心 + MCP/HTTP/CLI 多适配、Context Bundle | |
| Phase 3 | 主动关联提醒（行为关联，依赖使用数据） | |
| Phase 4 | 跨项目模式挖掘、个人技术风格画像 | |

对比原路线（时间维度 → 主动关联 → 模式挖掘 三段式），本次修订把"结构关联图谱"从原来的 Phase 1（关联图谱层）提前融合进 Phase 1 的核心交付物，而不是作为独立后置阶段；"事件溯源/时间维度"的能力拆分到 Phase 1（DesignDecision/CommitEvent 建模）和 Phase 3（面向个人使用习惯的历史查询）两处，不再作为单一 Phase 存在。

## 九、风险清单（更新）

| 风险 | 等级 | 应对 |
|---|---|---|
| 范围膨胀 | 高 | 本文档的定位收敛 + Phase 划分是主要应对手段 |
| 本地模型性能 | 高 | L0-L3 分级策略 |
| 检索质量 | 高 | 轻量/深度双路径 + Reranker |
| 数据污染 | 中 | Memory 生命周期字段（confidence/contradiction_score） |
| MCP 协议变化 | 中 | Memory Engine / Adapter 解耦，MCP 只是其中一个 Adapter |
| 图谱技术选型冒进 | 中 | Phase 0-3 仅用 SQLite，延迟引入图数据库 |
