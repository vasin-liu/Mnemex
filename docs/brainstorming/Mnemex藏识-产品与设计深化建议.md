# Mnemex / 藏识 — 产品与设计深化建议

> 本文基于 2026 年个人知识管理（PKM）、AI Agent 记忆基础设施、MCP 协议生态的最新动态，对此前的架构设计、路线图与视觉设计做进一步完善。

---

## 一、行业趋势速览（截至 2026 年 7 月）

**1. PKM 正从"存储检索"转向"语义关联 + 主动推送"**
Obsidian/Notion/Tana 等主流工具的共识是：AI 原生的语义搜索和自动摘要正在替代关键词检索成为标配，但真正的差异化在于"主动浮现相关信息"而非被动等待提问——这与你此前确定的"主动关联提醒"能力方向完全一致，说明这不是一个可选特性，而是这类产品能否留存用户的核心。同时行业也在强调"知识健康度监控"——自动标记过时或矛盾的内容，这是目前你的架构里缺失的一环。

**2. Agent 记忆已成为独立的工程学科，而非附属功能**
2026 年出现了专门评测记忆系统的基准测试（如 LoCoMo，覆盖多会话对话记忆召回），记忆层的评测已经标准化。同时，记忆框架生态高度碎片化——不同 agent 框架（LangChain、LangGraph、Mastra 等）互不兼容，主流记忆中间件不得不同时对接十几个框架。这对你的启示是：**MCP 只是暴露记忆的其中一种协议，不应该是唯一协议**。

**3. MCP 协议本身正在经历关键转折——协议层"去状态化"**
2026 年 7 月的 MCP 规范候选版本（2026-07-28 RC）核心变化是协议层转向无状态：不再假设服务端在多次工具调用之间隐式保留会话状态（比如当前仓库路径、当前任务），而是要求客户端显式传递、服务端显式声明可见的"作用域/句柄"。这直接影响你此前设计的 `get_active_context_alerts` 这类依赖"当前编辑上下文"的 MCP tool——不能再假设 MCP Server 端悄悄记着"用户现在在看哪个文件"，必须让调用方每次显式传入上下文句柄。

**4. MCP 生态规模已经很大，但企业级能力（审计、多租户、成本归因）仍是空白**
对个人桌面场景影响不大，但如果未来考虑团队协作方向，这些是需要提前预留的扩展点。

## 二、产品业务方向建议

### 2.1 明确"非泛用 PKM"的定位
Obsidian、Notion、Tana 已经把通用知识管理这个赛道占得很满。Mnemex/藏识 不应该和它们正面竞争"笔记工具"这个心智，而应该锚定一个更窄但更硬核的定位：**面向工程师/技术负责人的"代码+文档统一记忆层"，并且原生可被 AI Agent 调用**。这是 Obsidian 生态目前没有真正做好的——它们的 AI 插件普遍不处理代码符号级关联，也没有把自己暴露为 agent 可调用的记忆服务。这条差异化路径要在所有对外表达（文案、官网、README）里反复强调，避免被误认成"又一个 AI 笔记本"。

### 2.2 增加"知识健康度"能力
新增一类后台任务：定期检测知识库中的"过时/矛盾"信号——比如某个函数已被重构但相关设计文档没有更新，或者两份文档对同一个技术决策给出了不同的结论。这不是锦上添花，是让用户敢于长期依赖这套系统的信任基础：没有人愿意依赖一个会给出过时信息的"记忆"。

### 2.3 保留"意外发现"（serendipity）机制
行业访谈里提到一个值得借鉴的细节：把 AI 摘要的"创造性温度"在特定场景调高，主动推荐一些和当前任务不直接相关、但可能有启发性的历史记录或跨项目模式，避免系统因为过度贴合"当前任务相关性"而让用户错过意外的关联。可以设计成一个可选的"每周回顾"卡片，弱相关但可能有价值的内容单独呈现，不和主检索流程混在一起。

## 三、功能建议补充

| 功能 | 说明 | 优先级 |
|---|---|---|
| 知识健康度扫描 | 定期检测摘要/文档与实际代码的一致性偏差，标记"可能过时" | 高（建议纳入 Phase 3） |
| 显式上下文句柄 | MCP tool 调用需要显式传入 `scope_id`（如仓库路径+分支），服务端不再隐式记忆会话状态 | 高（协议兼容性，阻断项） |
| 双协议暴露 | 除 MCP 外，额外暴露一个轻量本地 HTTP/JSON API，供不支持 MCP 的框架直接调用 | 中 |
| 检索质量自评 | 内置类似 LoCoMo 思路的小型评测集（用户自己标注"这次检索有没有用"），用于持续调优排序权重 | 中 |
| 每周意外发现卡片 | 独立于主检索流程的"弱相关但可能有启发"内容推送 | 中 |
| 团队协作预留位 | 暂不做多用户，但数据模型和 MCP scope 设计上预留"多租户"扩展空间，避免未来推倒重来 | 低（架构预留，不实现） |

## 四、UI 方向补充

在此前的主界面基础上，本轮新增三类界面，覆盖"全屏关联图谱""隐私与推理控制""空状态/首次引导"，弥补此前只做了仪表盘单一视图的不足：

1. **关联图谱全屏视图**（`graph-view.html`）——从 mini 预览升级为可探索的全屏图谱，支持按类型筛选节点（文档/代码/决策记录），点击节点下钻。
2. **隐私与推理设置面板**（`privacy-panel.html`）——把"本地默认、云端可选、目录级强制本地"这条核心卖点做成一个用户能直接感知和控制的界面，而不是藏在深层设置里。
3. **空状态/首次运行引导**（`onboarding.html`）——新用户第一次打开时，索引尚未建立，这个状态如果做成单纯的"加载中"会显得空洞；应该用引导式文案说明"系统正在了解你"，把等待过程转化为信任建立的过程。

设计语言延续既有的液态玻璃 token（见《藏识Mnemex-UI设计规范.md》），不引入新的色彩体系。

## 五、技术方向调整

1. **MCP Server 改为显式作用域设计**：所有依赖"当前上下文"的 tool（如主动关联提醒）都必须接受一个显式 `scope` 参数（工作区路径 + 可选分支/提交），不能依赖服务端会话记忆。这是为了兼容 2026-07-28 之后的 MCP 协议方向，越早调整越省迁移成本。
2. **记忆层与协议层解耦**：核心的分层摘要、向量检索、关联图谱应该是独立于 MCP 的本地服务（比如一个本地 gRPC/HTTP daemon），MCP Server 只是这个 daemon 之上的一层协议适配器。这样未来接入非 MCP 框架（LangChain/LangGraph 等）时，只需要多写一层适配器，核心逻辑不用动。
3. **评测驱动的检索调优**：借鉴 LoCoMo 一类基准测试的思路，为自己的检索质量建一个小型内部评测集（哪怕只有几十条你自己标注的"应该检索到什么"样例），作为每次调整分块策略/排序权重后的回归测试，避免"感觉变好了"这种无法验证的迭代。

---

## 六、创意方向

- **"藏识周报"**：每周自动生成一份简报，包含本周新增的关联、识别出的模式、以及一条"意外发现"，作为用户与系统之间的仪式感触点，而不只是一个工具。
- **记忆呼吸感**：签名视觉元素（呼吸中的记忆核心）可以延伸出声音层——比如索引完成时有一个极简、克制的提示音（可选关闭），强化"系统在安静工作"的存在感，但绝不做打扰式通知音。
- **命名延伸**：如果未来拆分出团队版/云同步版，可以用"藏识·联"或"Mnemex Link"这类后缀，保持主品牌不变、只在能力边界上做区分，避免主产品的极简定位被稀释。
